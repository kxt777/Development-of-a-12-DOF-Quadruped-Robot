# dog_ik_walk 0.3.1 — command heading, IMU gaps and nearest-zero branch

## 0.3.4 staged straight-heading response (2026-10-07)

The straight test `dog_walk_demo_20261007_034048.json` had fresh IMU data throughout. At an error of 4.915 degrees the issued yaw command was only 0.158 degrees/s, despite an immediate PD request near the existing full turn bank. The 0.4 s output filter and unfiltered gyro damping delayed/attenuated correction. This evidence identifies command-response weaknesses; it does not prove that mechanics, traction, or heading estimation have no remaining error.

The optional `heading.straight_response` configuration enables a continuous proportional turn scale: 3 degrees requests 60% of the already tested 0.15 rad/s turn bank, and 5 degrees requests 100%. There is no 3-degree activation deadband. The output filter time constant is 0.08 s, selected to reach more than two thirds of a sustained request in five 50 Hz ticks (100 ms). Gyro feedback is filtered at the 1.2 Hz gait frequency (`tau = 1/(2*pi*1.2)`); damping fades continuously to zero as heading error reaches 3 degrees, leaving it primarily for braking near the reference. These are controller tuning choices tied to the user's 3--5 degree response requirement and measured gait, not manufacturer motor ratings or a guarantee of physical heading response. The existing yaw-bank amplitude, motor gains, gait and calibration are preserved.

Manual `demo_left`, `demo_right`, `walk_left`, and `walk_right` keep the previously tested fixed-turn response. Each `demo_*` performs zero/stand/walk; each `walk_*` starts a finite walk from an already enabled standing posture. All service names remain under `/dog_ik_walk_imu`. Legacy deployments without `straight_response` retain their original PD behavior. IMU gaps still fade straight correction without reanchoring the command-time reference; the filtered gyro state resets on a new command or missing samples.

Changing response settings invalidates the trajectory-cache signature. Rebuild the isolated cache and verify MIT encoding, including the faster blend derivative, before selecting that deployment. `python -m dog_ik_walk.replay_heading --deployment CONFIG --recording REPORT --output DIRECTORY` uses only a `DryRunLink`, produces command comparisons, and checks encoding over the recorded inputs and direction-reversal extremes. It does not simulate the physical closed-loop response or prove that drift is corrected. Stage the version separately; do not reload a holding hardware controller just to activate a code edit.

0.3.1 allows missing IMU samples during a finite walk: the 100 ms freshness boundary now marks diagnostics rather than aborting walking. While no fresh sample is available, yaw correction smoothly fades to zero using the existing filter. Fresh data resumes correction toward the same command-time heading. The original 20-second sequence duration remains unchanged. A new heading command still needs a fresh sample to define its direction.

The 2026-10-07 real test exposed a stale CAN cache at enable: ID 6 initially reported model angle -6.19936 rad after enable, while the gain ramp held the pre-enable cached target +1.34585 rad (7.54521 rad error). The new enable sequence starts with zero gains, waits for updated enabled feedback, selects each encoder zero's nearest revolution and only then ramps gains while holding the post-enable measured position. Each zero operation reselects the nearest calibrated zero: `zero_session = zero_original + 2*pi*round((position-zero_original)/(2*pi))`. Feedback and subsequent stand/walk targets use that same session offset. The offset is fixed between alignment operations; no per-frame angle wrapping and no encoder-zero writes occur. Original calibration files and motor directions are preserved. Status records enable/zero branch selection for all motors. Firmware still does not expose individual CAN-frame ages; USB arrival freshness alone must not be interpreted as fresh per-motor measurements.

For each accepted external forward command (`demo` or `walk`), use the latest fresh mounted body orientation at ROS service callback receipt as the heading reference. Preserve that reference throughout zeroing, standing, waiting and walking. Internal demo transitions are not new direction commands. The next accepted external forward command reanchors to its own receipt-time heading. A rejected command does not replace the target. Standing, stopping, disabling and receiving new IMU samples do not reanchor it.

`heading.command` in status and `heading_command` in demonstration reports record the command sequence, source, receipt monotonic time, IMU receipt monotonic time and target yaw. `step()` compares that fixed target against live mounted heading. Reference updates and control calculations share a lock; a queued walk cannot begin before its reference is committed. No reference is automatically assigned by the monitor-only IMU callback.

An external command uses the latest accepted IMU sample, so this is an approximation of the command-time physical heading at the sensor's sample resolution, not a measurement from an earlier preparation stage or a later walk start. Existing freshness checks apply when capturing the command. Subsequent live samples must also stay fresh for correction. A captured target remains valid while preparing even though its original sample becomes old.

The existing interface is a finite 20-second forward walk/demo, not a general velocity-command stream. A new demo/walk during an active demo is still rejected by the existing sequence arbitration. Only accepted external direction commands update the reference; stop/disable remain available. This change does not extend walking indefinitely or add lateral position estimation.

ROS nodes and interfaces retain the `dog_` prefix. Deployment defaults to `allow_actuation:=false`; no motor port is opened in that mode. Hardware motion requires a separate user instruction.

Regression tests cover command t1 followed by a heading change during preparation, t2 reanchoring, queued start without recapture, internal demo transitions, stale/rejected commands, and angle wrapping/correction direction. Tests use fake controllers and never open serial ports.
